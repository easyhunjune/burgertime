# 버거타임 측정기

한국 새벽(미국 업무시간)에 Claude Code와 Codex CLI가 실제로 느려지거나 덜 똑똑해지는지 직접 재는 도구입니다.
맥에서 launchd로 주기적으로 돌리고, 몇 주 쌓인 기록을 `analyze.py`로 시간대별로 비교합니다.
Python 표준 라이브러리만 씁니다 (3.9 이상).

## 무엇을 재나

| 측정 | 기본 주기 | 내용 | 쿼터 소모 |
|---|---|---|---|
| ping | 20분마다 (24시간) | "pong" 한 단어만 답하게 함. 첫 응답까지 시간, API TTFT(Claude), 오류 | 아주 적음 |
| quality | 6시간마다 (매일 03·09·15·21시 KST) | 코딩 과제 3개를 CLI가 직접 풀고, 숨은 테스트로 채점 | 큼 |

quality 과제는 매번 같은 3개입니다. 점수는 통과/실패가 아니라 숨은 테스트 통과 비율이라 조금씩 놓치는 것도 잡힙니다.

- `cron_next`: cron 식의 다음 실행 시각 계산기를 명세대로 구현. `L`/`W`/`#` 확장, 일·요일 OR 규칙 (숨은 테스트 80개)
- `sheet_engine`: 스프레드시트 수식 엔진 구현. 순환 참조, 오류 전파, 999칸 의존 사슬 (100개)
- `patch_apply`: 버그 10여 개가 숨은 unified diff 적용기 고치기. 눈에 보이는 실패 테스트는 1개뿐 (41개)

`tasks/`에는 처음 쓰던 쉬운 과제 3개(`duration_spec`, `ledger_fifo`, `expr_eval`)도 남아 있지만 측정에는 쓰지 않습니다.
첫 측정에서 두 모델 모두 만점이었기 때문입니다. 어려운 3개도 첫 측정은 만점이었습니다. 그래서 판정은 점수가 아니라
thinking 토큰·소요 시간·응답 속도·오류율로 합니다 (아래 "분석 기준").

기록마다 함께 남는 것:

- **실제로 돈 모델**: Claude는 API 응답에 찍힌 model, Codex는 세션 로그(`~/.codex/sessions`)의 model과 effort. Astra를 골랐는데 Sol이 돈 경우는 `model_mismatch`로 표시됩니다.
- thinking 토큰(Claude `thinkingTokens`, Codex `reasoning_output_tokens`), 출력 토큰, 캐시 적중 토큰
- 사용량 한도 사용률(5시간·주간), CLI 버전, 한국 시각, 미국 태평양시 요일

quality 간격(`quality_every_hours`)은 UTC 기준 시각을 나눈 나머지로 정해집니다. 6처럼 24의 약수면 매일 같은 시각에만
돌고(지금: 03·09·15·21시 KST), 5·7처럼 24와 서로소면 매일 시각이 밀리면서 며칠에 걸쳐 24시간대를 모두 돕니다.
지금은 날마다 같은 시각끼리 비교하려고 6을 씁니다. 03시는 미국 서부 오전 11시(업무 피크), 15시는 미국 서부 밤 11시입니다
(2026-11-01 미국 서머타임이 끝난 뒤에는 각각 오전 10시·밤 10시).

## 준비

1. 이 폴더를 **홈 바로 아래**에 둡니다. 예: `~/burgertime`
   (데스크탑·문서·다운로드·iCloud 폴더는 macOS가 백그라운드 접근을 막아서 launchd 실행이 실패합니다.)
2. 터미널에서 `claude`와 `codex`가 둘 다 로그인돼 있어야 합니다. 한 번씩 실행해서 확인하세요.
3. `python3 --version`이 3.9 이상이면 됩니다. 없으면 `xcode-select --install`.
4. **launchd용 Claude 토큰**: launchd로 도는 작업은 로그인 키체인의 Claude 로그인을 못 읽거나 만료된 것을 읽을 수 있습니다. `claude setup-token`으로 만든 토큰을 `config.json`의 `env_file`(기본 `.env`)에 `CLAUDE_CODE_OAUTH_TOKEN=...` 한 줄로 넣으세요. 측정기는 이 파일에서 `CLAUDE_CODE_OAUTH_TOKEN` 하나만 읽고, 값은 어디에도 출력하지 않습니다. 이미 같은 토큰을 둔 다른 `.env` 파일이 있으면 `env_file`에 그 경로를 적어도 됩니다. 그 파일에 다른 키가 있어도 읽지 않습니다. `selftest`에 토큰이 있는지 나옵니다.
5. `config.json`의 `bin`은 Homebrew로 설치한 macOS 기준 경로입니다(`/opt/homebrew/bin/claude`, `/opt/homebrew/bin/codex`). 자기 환경에 맞게 바꾸세요. ChatGPT 데스크톱 앱이 설치하는 `~/.local/bin/codex`가 PATH에서 먼저 잡힐 수 있는데, 앱과 함께만 업데이트되는 이전 버전(측정 시작 시점 0.148 알파)은 gpt-6 모델을 거부하므로 절대경로로 지정하는 편이 안전합니다.

## 설치 순서

```bash
cd ~/burgertime
python3 run_bench.py selftest               # 채점기와 CLI 점검. 쿼터 0
python3 run_bench.py ping                   # 실제 호출 1번씩. 쿼터 거의 0
python3 run_bench.py calibrate --repeat 1   # 과제 3개 x 대상 2개를 한 번 풀게 함. 쿼터 큼
chmod +x install.sh uninstall.sh
./install.sh
```

`calibrate`는 꼭 한 번 돌려 보세요. 확인할 것은 네 가지입니다.

- 두 CLI 모두 "파일 변경 없음" 경고 없이 과제를 실제로 풀었는지 (권한·샌드박스 문제 확인)
- `권한거부` 열이 0인지. 0이 아니면 Claude가 `python3`로 테스트를 못 돌린 채 풀었다는 뜻입니다.
- 점수가 늘 1.00(천장)인지. 천장이면 정답률로는 차이가 안 보이고 thinking 토큰·시간으로 봐야 합니다.
- 한 번 돌린 뒤 `results/runs.jsonl`의 `rl_5h_util`/`rl_7d_util`이 얼마나 올랐는지 → quality 1회 비용

설치 후 1~2분 뒤 `python3 run_bench.py status`로 첫 ping이 찍혔는지 확인하세요.

## 맥이 잠들면 기록이 비어요

버거타임 측정은 새벽에 맥이 깨어 있어야 의미가 있습니다.

- 전원을 연결하고, 시스템 설정 → 배터리(데스크탑은 에너지) → **디스플레이가 꺼져 있을 때 자동으로 잠자기 방지**를 켭니다.
- 노트북 뚜껑을 닫으면(외부 모니터가 없으면) 잠듭니다.
- **로그아웃하면 안 됩니다.** Claude 로그인 정보가 로그인 키체인에 있어서 로그아웃 상태에선 호출이 실패합니다. 화면 잠금은 괜찮습니다.
- 잠들었다 깬 직후의 실행은 `after_gap`으로 표시되고 분석에서 기본 제외됩니다.

## 쿼터

- quality 한 번 = 과제 3개 × 대상 2개. **평소 내가 쓰는 사용량 한도를 같이 깎습니다.** 같은 계정으로 다른 도구나 봇을 돌리고 있다면 그것들과도 한도를 나눠 씁니다.
- 실측(Codex Plus, Astra high): 과제 6개를 한 번 돌리니 5시간 한도의 약 25%, 주간 한도의 약 4%를 썼습니다. 어려운 3개만이면 그 3분의 2쯤(5시간 약 16%, 주간 약 2.5%)으로 추정되고, 6시간 간격(하루 4회)이면 주간 한도를 하루 약 10% 씁니다. Claude는 과제 6개에 5시간 약 3%, 주간 약 1%였습니다.
- 한도가 빠듯하면 `quality_every_hours`를 늘리세요. 단 측정 시각 구성이 바뀌므로 아래 "분석 기준"의 변경 기록에 남겨야 합니다.
- 한도에 걸린 실행은 점수 0이 아니라 `rate_limited` 상태로 따로 집계되고, 버거타임 판단(서버 오류율)에서도 빠집니다. 사용률 95% 이상에서 찍힌 기록도 분석에서 기본 제외됩니다.

## 분석

```bash
python3 analyze.py
python3 analyze.py --burger 0-5 --since 2026-10-20 --csv out.csv
```

- 대상별로 한국시간 0~23시 표가 나옵니다. `*`가 버거타임(기본 01~06시)입니다.
- "버거타임 vs 나머지"에서 서버 오류율 차이, 첫 응답 시간 비율, 점수 차이(과제 난이도 보정), thinking 토큰·도구 호출 수 비율을 비교합니다. 대괄호는 95% 신뢰구간이고 `<- 유의`가 붙으면 우연으로 보기 어려운 차이입니다.
- 신뢰구간은 **묶음 단위**로 계산합니다. 한 번의 과제 실행에서 나온 기록들, 같은 날의 ping들은 같이 움직이기 때문에 하나하나를 독립 표본으로 치면 하룻밤 사고 하나가 "유의"로 나옵니다. 그래서 quality는 실행 단위, ping은 날짜 단위로 묶고, 최소 표본(`--min-n`, 기본 10)도 묶음 수 기준입니다. ping은 10일, quality는 버거타임 실행 10회(03시 측정이 하루 1번이라 10일)가 쌓여야 판정이 나옵니다.
- **서버 오류율**은 overloaded·timeout·CLI 오류만 셉니다. 사용량 한도(`rate_limited`)는 내가 언제 많이 쓰느냐에 따라 생기므로 따로 개수만 보여 주고 판단에서는 뺍니다.
- "미국 평일만"도 따로 봅니다. 버거타임 가설이 맞다면 미국 주말보다 평일에서 차이가 더 커야 합니다.
- 기본으로 빼는 기록: 손으로 돌린 것·calibrate(한 시각에 몰려 있음, `--all-triggers`로 포함), 맥이 잠들었다 깬 직후(`--include-after-gap`), 과제 실행 중에 찍힌 ping(같은 계정에 요청이 몰린 상태, `--include-overlap`).
- Codex의 thinking 토큰(`reasoning_output_tokens`)은 실제 추론량보다 훨씬 작게 찍혀서(high effort 95초 과제에 146) 참고용입니다. Codex는 도구 호출 수·소요 시간·출력 토큰을 더 믿으세요.
- 최소 2~3주는 쌓으세요.

## 분석 기준 (사전 등록)

결과를 보기 전에 정해 둔 판정 기준입니다. 결과를 본 뒤 구간이나 지표를 바꾸면 "원하는 결과가 나올 때까지 고른 것"이
되므로, 이 기준은 기간이 끝날 때까지 바꾸지 않습니다. 부득이하게 바꾸면 맨 아래 변경 기록에 날짜와 이유를 남깁니다.

**등록 시점:** 2026-10-13 03:46 KST, 첫 정식 측정 구간(09:00) 전.
등록 전에 본 데이터는 calibrate 1회(01:28)와 03:14 과제 측정 1회의 점수·시간(모두 만점), 그리고 핑 14회 로그입니다.
시간대 비교(`analyze.py`)는 한 번도 돌리지 않았습니다. 이 기록들은 분석 구간 밖이라 판정에 쓰지 않습니다.

### 가설

- 버거타임(한국시간 01:00~06:59, 미국 업무시간)에는 나머지 시간보다 응답이 느리거나, 서버 오류가 많거나,
  추론량(thinking 토큰)이 적거나, 과제를 푸는 데 더 오래 걸린다.
- 귀무가설: 차이가 없다. 반대 방향(버거타임이 더 좋음)으로 나와도 그대로 보고한다.

### 측정 구성 (기간 중 고정)

- 대상: `claude-opus-5-5`(effort high), `gpt-6-astra`(effort high). 핑은 effort low.
- 과제: `cron_next`, `sheet_engine`, `patch_apply`. 과제 파일과 프롬프트는 고정한다(과제 파일·task.json 프롬프트는 `task_version`으로,
  공통 머리말·CLI 옵션은 run_bench.py의 커밋으로 확인).
- 간격: 핑 20분(24시간), 과제 6시간(매일 03·09·15·21시 KST).
- CLI 자동 업데이트는 통제하지 않는다. 버전은 기록에 남고 보고서에 같이 적되, 그것만으로 기록을 빼지는 않는다.

### 분석 구간

- 전체: **2026-10-13 09:00 ~ 2026-11-10 09:00 KST (4주)**
- 반복 확인용 절반: 전반부 ~ 2026-10-27 09:00, 후반부 2026-10-27 09:00 ~

```bash
python3 analyze.py --since "2026-10-13 09:00" --until "2026-11-10 09:00"   # 판정
python3 analyze.py --since "2026-10-13 09:00" --until "2026-10-27 09:00"   # 전반부
python3 analyze.py --since "2026-10-27 09:00" --until "2026-11-10 09:00"   # 후반부
```

나머지 옵션은 모두 기본값입니다: 버거타임 `--burger 1-6`, `--min-n 10`, `--n-boot 1000`, `--seed 42`, `--max-util 0.95`.
과제 측정에서 버거타임은 03시 실행이고, 09·15·21시 실행이 나머지입니다.

### 판정에 쓰는 지표 (7개)

| 지표 | 대상 | 데이터 | `analyze.py` 출력 줄 | 의미 있는 최소 크기 |
|---|---|---|---|---|
| 첫 응답 시간 | Claude, Codex | ping | 첫 응답 시간 (중앙값 비) | 1.10x 이상 (또는 0.91x 이하) |
| 서버 오류율 | Claude, Codex | ping | 서버 오류율 차이 | +2%p 이상 (또는 -2%p 이하) |
| 과제 소요 시간 | Claude, Codex | quality | 소요 시간 (중앙값 비) | 1.10x 이상 (또는 0.91x 이하) |
| thinking 토큰 | Claude만 | quality | thinking 토큰 (중앙값 비) | 0.85x 이하 (또는 1.18x 이상) |

Codex의 thinking 토큰은 실제 추론량을 반영하지 않는 것으로 보여 판정에서 뺍니다.

### 판정 규칙

각 지표마다:

1. 전체 구간의 "전체 요일" 비교에서 95% 신뢰구간이 기준선(1.00x 또는 0%p)을 포함하지 않는다 (`<- 유의`).
2. 점추정이 위 표의 최소 크기 이상이다.
3. "미국 평일만" 비교에서도 점추정의 방향이 같다.
4. 전반부와 후반부 각각에서도 점추정의 방향이 같다 (표본 부족으로 계산이 안 되면 불충족).

- 1~4를 모두 만족하면 **효과 있음**.
- 1과 2만 만족하면 **약한 신호**.
- 그 외는 **차이 없음(검출 못 함)**. 이때는 "최소 크기 이상의 차이는 관찰되지 않았다"고 쓴다.

판정 지표가 7개라 우연히 하나쯤 "유의"가 나올 확률이 낮지 않습니다(약 30%). 그래서 결론은 3·4번 조건까지 통과한
지표만으로 내고, 지표 하나만 통과했으면 그 점을 같이 밝힙니다.

### 판정에 쓰지 않고 보고만 하는 것

과제 점수(천장이라 신호가 없음), 도구 호출 수, 출력 토큰, Codex thinking 토큰, API TTFT, 과제 실행의 서버 오류율,
시간대별 표, 요청과 다른 모델이 돈 기록(`model_mismatch`, 나오면 시각 분포와 함께)입니다.

### 제외 규칙 (`analyze.py` 기본값)

- 손으로 돌린 실행과 calibrate
- 맥이 잠들었다 깬 직후의 실행
- 과제 실행 중에 찍힌 핑
- 사용량 한도 사용률 95% 이상에서 찍힌 기록
- 서버 오류율에서는 `rate_limited`(내 사용량 영향), `auth_error`(토큰 문제), `bench_error`(측정기 문제)를 분모에서도 뺀다.
- 서버 오류율을 뺀 지표(첫 응답 시간·소요 시간·thinking 토큰)는 성공(`ok`)한 기록만 쓴다.

## 해석할 때 주의

- **CLI 업데이트·모델 교체**는 시간대와 무관한 변화입니다. 분석 맨 위에 CLI 버전별 기간이 나오니, 바뀐 시점 이후만 보려면 `--since`를 쓰세요. `claude-opus-5-5`처럼 모델을 풀네임으로 고정해 둔 것도 그 때문입니다 (`opus` 같은 별칭은 새 모델이 나오면 가리키는 대상이 바뀝니다).
- **모델 바꿔치기 검출의 한계**: Codex는 클라이언트가 세션 로그에 적은 모델이라, 클라이언트 쪽에서 Sol로 돈 경우(openai/codex#42853 같은)는 잡지만 서버 내부에서 바꿔치기하는 건 못 잡습니다. Claude는 API 응답에 찍힌 model을 봅니다.
- **측정 환경 격리**: Claude는 `--safe-mode`(CLAUDE.md·MCP·훅·플러그인 끔)로, Codex는 `--ignore-user-config --ignore-rules`(config.toml과 실행 규칙 파일 무시)로 돌립니다. 내 설정을 바꿔도 결과에 섞이지 않게 하려는 것입니다. 다만 `~/.codex/AGENTS.md`는 여전히 읽힐 수 있으니 측정 기간엔 바꾸지 마세요.
- **권한**: 과제는 매번 새 임시 폴더에서 돕니다. Claude는 그 폴더의 파일 편집과 `python3`/`python` 실행만 허용되고, Codex는 workspace-write 샌드박스 안에서 돕니다.
- 같은 프롬프트를 반복하므로 프롬프트 캐시가 적용됩니다(`cached_input_tokens`로 기록).

## 명령

| 명령 | 하는 일 |
|---|---|
| `python3 run_bench.py selftest` | 채점기·CLI 점검 (쿼터 0) |
| `python3 run_bench.py ping` | 지금 ping 한 번 |
| `python3 run_bench.py quality [--target NAME] [--task ID]` | 지금 과제 실행 |
| `python3 run_bench.py calibrate --repeat N` | 과제 N번 반복해 난이도 확인 |
| `python3 run_bench.py status` | 최근 기록 보기 |
| `python3 analyze.py` | 시간대별 분석 |
| `./install.sh` / `./uninstall.sh` | launchd 등록 / 해제 (기록은 남음) |

## 설정 (`config.json`)

- `targets`: 측정 대상. `claude-fable`은 기본으로 꺼져 있습니다(`"enabled": false`). 켜려면 `true`로 바꾸고, 가능하면 모델 풀네임으로 고정하세요. 대상마다 `"bin"`(실행 파일 절대경로), `"extra_args"`, `"ping": false`, `"quality": false`를 줄 수 있습니다.
- `effort`: 과제용 추론 강도, `ping_effort`: ping용 (동봉 config.json 값은 low, 빼면 CLI 기본값)
- 그 밖에 `tasks`(쓸 과제 목록), `quality_every_hours`, `ping_timeout_sec`(180), `task_timeout_sec`(900), `keep_raw`(원본 출력 보관), `codex_ignore_user_config`가 있습니다.
- `codex_config_overrides`: Codex는 측정 격리를 위해 `config.toml`을 무시하므로, 꼭 필요한 설정만 여기에 `"키=값"` 문자열로 넣습니다. 맥은 비워 두면 됩니다. Windows에서 돌린다면 `["windows.sandbox=\"elevated\""]`가 없으면 샌드박스가 모든 명령을 막습니다.
- `ping_interval_min`을 바꿨으면 `./install.sh`를 다시 실행하세요. 나머지는 다음 실행부터 바로 반영됩니다.
- 과제 파일을 고치면 `task_version`이 바뀌어 기록에 남습니다.
