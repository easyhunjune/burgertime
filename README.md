# 버거타임 측정기

한국 새벽(미국 업무시간)에 Claude Code와 Codex CLI가 실제로 느려지거나 덜 똑똑해지는지 직접 재는 도구입니다.
맥에서 launchd로 주기적으로 돌리고, 몇 주 쌓인 기록을 `analyze.py`로 시간대별로 비교합니다.
Python 표준 라이브러리만 씁니다 (3.9 이상).

> **1차 측정 종료 (2026-10-13 ~ 11-10).** 결과는 바로 아래에 있습니다. 과제가 쉬워서 정답률로는 아무것도
> 볼 수 없었기 때문에, 더 어려운 과제로 2차 실험을 준비하고 있습니다.
>
> **2026-11-21 정정.** 측정이 실제로 서버를 재고 있는지 다시 검토했습니다. Claude 핑 판정을 "차이 없음"에서
> "판단 불가"로 고쳤고, Codex 핑 결과에 단계별로 나눠 본 사후 분석을 붙였습니다. 숫자와 판정 기준은 그대로입니다.

### 사후 분석 (2026-11-21, 판정과 별개)

결과를 본 뒤에 한 분석이라 판정에는 쓰지 않습니다. 판정과 같은 기록(Codex 1,987건, Claude 1,997건)을 썼고,
신뢰구간은 날짜를 통째로 다시 뽑는 방식(같은 날의 버거타임·나머지를 함께)입니다. 위 판정표와는 신뢰구간 계산 방식이 다릅니다.

### 이 측정이 잴 수 있는 것과 없는 것

- **잴 수 있는 것**: 이 맥(한국 가정집 회선)과 이 계정으로 CLI를 쓸 때 체감하는 응답 시간·과제 시간·thinking 토큰의
  시간대별 차이. 4주 동안 매일 같은 방향으로 나온 Codex 핑 차이처럼 꾸준한 차이는 잘 잡힙니다.
- **서버 탓인지 회선 탓인지**: 가를 수 없습니다. 첫 응답 시간에는 CLI 실행, 원격 동기화, 회선, 서버 대기, 생성이
  다 섞여 있습니다. 위 사후 분석으로 CLI 준비 구간은 떼어 냈지만 모델 응답 구간 안의 회선 몫은 남습니다.
- **모델이 덜 똑똑해졌는지**: 1차로는 볼 수 없었습니다. 과제 점수가 거의 다 만점이었습니다(과제 기록 Codex 332건 전부,
  Claude 309건 중 306건).
- **짧은 서버 장애**: CLI가 내부에서 재시도하므로 대부분 실패가 아니라 지연으로만 남습니다.
- **내 사용량**: 측정 계정은 평소 내가 쓰는 계정이라 내 사용이 섞일 수 있습니다. 1차 기록에서 그 사이 계정이 쓰인
  ping을 빼고 다시 판정해도 판정 7개가 그대로였습니다(아래 2차 실험의 민감도 분석). 한도에 닿는 경우는 사용량 95% 이상
  제외 규칙으로 뺍니다.
- Claude는 첫 응답을 첫 메시지 이벤트로, Codex는 첫 완료 항목으로 재서 끝점이 다릅니다. 두 CLI의 절대 시간을 서로
  비교하는 데는 쓰지 마세요. 각 CLI 안에서 시간대끼리 비교하는 용도입니다.
- 한 계정, 한 장소, 대상마다 구독 플랜 하나입니다.

### 판정에 쓰지 않고 보고만 하는 것

- **과제 점수**: Codex는 기간 내내 과제 3개 모두 만점이었습니다. Claude도 `sheet_engine`에서 0.99가 3번(매번 같은 케이스
  `if_range_branch`) 나온 것 말고는 전부 만점입니다. 정답률로는 차이를 볼 수 없었고, 이게 2차 실험을 하는 이유입니다.
- 도구 호출 수: 두 모델 모두 1.000x
- 출력 토큰: Claude 0.998x, Codex 1.035x [1.009 ~ 1.079] (신뢰구간은 1을 벗어나지만 판정 지표가 아니고 크기도 3.5%)
- Codex thinking 토큰: 전체 1.115x, 전반부 1.261x(유의), 후반부 0.989x. 실제 추론량을 반영하지 않는 값이라 판정에서 뺐습니다.
- Claude API TTFT: 0.911x [0.763 ~ 1.187]
- 과제 실행 서버 오류: Claude 0건, Codex 1건(10-18 21시 overloaded)
- 요청과 다른 모델이 돈 기록(`model_mismatch`): 두 모델 모두 0건
- 시간대별 표 전체: [`data/round1/analysis_full.txt`](data/round1/analysis_full.txt)

### 기록과 제외

- 구간 안 정기 기록 4,682건(핑 4,010, 과제 672) 중 4,631건을 썼습니다. 뺀 것: 사용량 95% 이상 23건, advisor가 섞인
  Claude 과제 24건(변경 기록 10-21), 과제 실행과 겹친 핑 4건. 손으로 돌린 실행 2건은 원래 판정 대상이 아닙니다.
- 11-10 03시 Claude 과제 실행은 측정기 밖에서 같은 계정을 많이 써서 5시간 한도에 걸렸습니다(같은 시각 Claude 핑 3건도).
  95% 규칙으로 빠졌고, 그래서 버거타임 과제 실행은 Claude 25회, Codex 28회입니다.
- CLI 자동 업데이트는 막지 않았습니다. Claude Code는 2.1.291 → 2.1.316(6개 버전), Codex CLI는 0.160.1 → 0.167.0(11-09)입니다.
  한 버전이 하루 24시간을 다 돌기 때문에 버거타임 비교에는 크게 섞이지 않지만, 버전마다 핑 프롬프트 크기가 조금씩 달랐습니다.
- 한 계정, 한 장소(한국의 맥 한 대), 대상마다 구독 플랜 하나로 잰 결과입니다. 다른 플랜·지역에서는 다를 수 있습니다.

### 2차 실험 (준비 중)

1차는 "느려지는가"에는 답했지만, 과제가 쉬워서 "멍청해지는가"는 볼 수 없었습니다. 2차는 두 모델이 만점을 못 받는
과제로 정답률 자체를 비교하는 게 목표입니다. 과제 후보는 측정을 시작하기 전에 calibrate로 난이도를 확인해 거르고,
판정 기준은 1차처럼 시작 전에 따로 등록합니다. 1차의 과제·기준·기록은 그대로 둡니다.

위 재검토를 반영해 측정기를 이렇게 바꿨습니다(측정기는 아직 꺼져 있습니다).

- **핑을 단계별로 기록**: Codex는 세션 로그 시각으로 CLI 준비(`t_prep_sec`)와 모델 응답(`t_model_sec`)을 나누고,
  Claude는 CLI 초기화까지(`t_boot_sec`)와 API TTFT(`t_model_sec`)를 남깁니다.
- **통신 시간을 따로 잼**: 핑 직전에 API 호스트(api.anthropic.com, chatgpt.com)까지 DNS·TCP·TLS·첫 바이트 시간을
  재서(`net_*`, 인증 없이 HEAD 한 번) 회선 쪽 변화를 따로 봅니다.
- **Codex 요청 고정**: `features.remote_plugin=false`, `features.apps=false`, `features.plugins=false`로 원격 플러그인
  목록이 끼어드는 걸 막습니다. 시험 핑에서 `remote_plugin`만 끄면 여전히 섞여 들어갔고, 셋 다 끄면 요청이 한 가지로
  고정됐습니다. 요청 구성의 해시(`prompt_hash`)도 기록합니다. 그래서 2차의 Codex 첫 응답 시간은 1차와 직접 비교하지 않습니다.
- **CLI 버전**: 측정기가 띄운 CLI는 자동 업데이트를 끄고(`DISABLE_AUTOUPDATER`), 고정할 버전을 config에 적으면 다른 버전으로
  돈 기록에 `version_drift`를 남깁니다. 측정기 밖에서 CLI가 업데이트되는 것까지는 막지 못합니다
  (1차가 끝난 뒤에도 Claude Code 2.1.316 → 2.1.327, Codex CLI 0.167.0 → 0.170.0으로 바뀌어 있었습니다).
- **과제는 두 CLI를 차례로**: 동시에 돌리면 서로 CPU를 나눠 써서 정해진 시간 안에 계산하는 과제의 점수가 흔들립니다.
  먼저 도는 쪽은 매번 섞고(`cli_order`), 예정 시각(`slot_kst_hour`)을 기록해 두 번째 대상이 늦게 시작해도 같은 시간대로 봅니다.
- **제한시간에 걸린 과제도 점수에 포함**: 1차 규칙은 성공한 실행만 써서, 제한시간에 걸린 실행은 점수가 있어도 빠졌습니다.
  2차는 "정해진 시간 안에 만든 결과물의 점수"로 보고 `analyze.py --score-timeouts`로 포함합니다. 제한시간에 걸리면 최종
  thinking 토큰 보고가 없어서, 실행 중에 흘러나온 추정치(`thinking_tokens_est`)를 씁니다.
- **나중에 다시 채점**: 작업 폴더는 zip으로 남아 있으므로 `run_bench.py regrade`로 조용할 때 하나씩 여러 번 다시 채점하고,
  `analyze.py --regrade`로 그 중앙값을 씁니다. 채점 당시 부하와 채점 시간(`load_avg_1m`, `grade_wall_sec`, `grade_cpu_sec`)도 남깁니다.
  2차 과제 calibrate 1회(11-10)의 작업 폴더를 3번씩 다시 채점해 보니, `vrptw_opt`는 Claude 0.7065(실시간) → 0.7165·0.713·0.7065,
  Codex 0.5195 → 세 번 모두 0.5195였고 나머지 과제는 모두 실시간 점수와 같았습니다. 채점 자체의 흔들림은 1%p 안팎입니다.
- **사용량**: 2차 과제는 Codex 과제 1개에 주간 한도의 약 2.7%가 들어, 하루 1~2개가 한계입니다.

2차 기준을 등록할 때 넣을 것 (2026-11-21 정함):

- **민감도 분석: 내 사용량을 뺀 판정**. 측정 계정은 평소 내가 쓰는 계정이라, 내 사용이 측정에 섞일 수 있습니다.
  그래서 2차는 판정을 두 번 냅니다.
  - 본 판정: 1차처럼 모든 ping으로 냅니다.
  - 민감도 판정: 같은 등록 명령에 `--drop-active-pings`를 붙여, 직전 기록보다 계정의 5시간 사용량이 3%p 이상 오른 ping을
    빼고 다시 냅니다. 측정기 ping 하나는 5시간 사용량을 거의 움직이지 않으므로(1차에서 직전 ping과의 차이가 ±1%p 이내인
    경우가 Claude 79%, Codex 89%), 그만큼 올랐다면 그 사이에 누군가 계정을 쓴 것입니다. 직전 기준점과의 사이에 같은 CLI의
    측정기 과제가 있었거나 기준점이 60분보다 오래됐으면, 과제가 쓴 양과 나눌 수 없어서 판단하지 않고 남깁니다.
  - 결론: ping 지표의 판정 이름이 두 판정에서 같으면 그대로 씁니다. "효과 있음"과 "약한 신호"로 갈리면 "약한 신호",
    그 밖의 조합으로 갈리면 "판단 불가"로 결론 짓고 두 판정을 함께 적습니다. 과제 지표는 이 분석으로 바뀌지 않습니다
    (ping만 뺍니다). 과제는 사용량 95% 이상 제외 규칙만 적용합니다.
  - 1차 기록에 참고로 돌려 보면 Claude ping 178건, Codex ping 37건이 빠지고 판정 7개가 모두 그대로입니다.
    Claude 핑 첫 응답은 0.939배에서 0.901배 [0.760~1.090]로 바뀌지만 "판단 불가" 그대로이고, Codex는 0.735배에서 0.736배로
    "효과 있음" 그대로입니다. Claude는 빠진 ping이 버거타임에 몰렸습니다(버거타임 17%, 나머지 6%). 새벽에 계정을 더 많이
    썼기 때문입니다.

## 무엇을 재나

| 측정 | 기본 주기 | 내용 | 쿼터 소모 |
|---|---|---|---|
| ping | 20분마다 (24시간) | "pong" 한 단어만 답하게 함. 첫 응답까지 시간, API TTFT(Claude), 오류. 2차부터 단계별 시간과 API 호스트까지의 통신 시간도 | 아주 적음 |
| quality | 6시간마다 (매일 03·09·15·21시 KST) | 코딩 과제 3개를 CLI가 직접 풀고, 숨은 테스트로 채점 | 큼 |

아래는 1차에 쓴 과제입니다. 2차용 과제(`regex_engine`, `vrptw_opt`, `interp_bugs`)는 준비 중이고, 어떤 과제를 쓸지는
2차 기준을 등록할 때 여기에 정리하면서 저장소에도 올립니다.

quality 과제는 매번 같은 3개입니다. 점수는 통과/실패가 아니라 숨은 테스트 통과 비율이라 조금씩 놓치는 것도 잡힙니다.

- `cron_next`: cron 식의 다음 실행 시각 계산기를 명세대로 구현. `L`/`W`/`#` 확장, 일·요일 OR 규칙 (숨은 테스트 80개)
- `sheet_engine`: 스프레드시트 수식 엔진 구현. 순환 참조, 오류 전파, 999칸 의존 사슬 (100개)
- `patch_apply`: 버그 10여 개가 숨은 unified diff 적용기 고치기. 눈에 보이는 실패 테스트는 1개뿐 (41개)

`tasks/`에는 처음 쓰던 쉬운 과제 3개(`duration_spec`, `ledger_fifo`, `expr_eval`)도 남아 있지만 측정에는 쓰지 않습니다.
첫 측정에서 두 모델 모두 만점이었기 때문입니다. 어려운 3개도 첫 측정은 만점이었습니다. 그래서 판정은 점수가 아니라
thinking 토큰·소요 시간·응답 속도·오류율로 합니다 (아래 "분석 기준").

기록마다 함께 남는 것:

- **실제로 돈 모델**: Claude는 API 응답에 찍힌 model, Codex는 세션 로그(`~/.codex/sessions`)의 model과 effort. Astra를 골랐는데 Sol이 돈 경우는 `model_mismatch`로 표시됩니다.
- thinking 토큰(Claude `thinkingTokens`, Codex `reasoning_output_tokens`), 출력 토큰, 캐시 적중 토큰
- 사용량 한도 사용률(5시간·주간), CLI 버전, 한국 시각, 미국 태평양시 요일

quality 간격(`quality_every_hours`)은 UTC 기준 시각을 나눈 나머지로 정해집니다. 6처럼 24의 약수면 매일 같은 시각에만
돌고(지금: 03·09·15·21시 KST), 5·7처럼 24와 서로소면 매일 시각이 밀리면서 며칠에 걸쳐 24시간대를 모두 돕니다.
지금은 날마다 같은 시각끼리 비교하려고 6을 씁니다. 03시는 미국 서부 오전 11시(업무 피크), 15시는 미국 서부 밤 11시입니다
(2026-11-01 미국 서머타임이 끝난 뒤에는 각각 오전 10시·밤 10시).

## 준비

1. 이 폴더를 **홈 바로 아래**에 둡니다. 예: `~/burgertime`
   (데스크탑·문서·다운로드·iCloud 폴더는 macOS가 백그라운드 접근을 막아서 launchd 실행이 실패합니다.)
2. 터미널에서 `claude`와 `codex`가 둘 다 로그인돼 있어야 합니다. 한 번씩 실행해서 확인하세요.
3. `python3 --version`이 3.9 이상이면 됩니다. 없으면 `xcode-select --install`.
4. **launchd용 Claude 토큰**: launchd로 도는 작업은 로그인 키체인의 Claude 로그인을 못 읽거나 만료된 것을 읽을 수 있습니다. `claude setup-token`으로 만든 토큰을 `config.json`의 `env_file`(기본 `.env`)에 `CLAUDE_CODE_OAUTH_TOKEN=...` 한 줄로 넣으세요. 측정기는 이 파일에서 `CLAUDE_CODE_OAUTH_TOKEN` 하나만 읽고, 값은 어디에도 출력하지 않습니다. 이미 같은 토큰을 둔 다른 `.env` 파일이 있으면 `env_file`에 그 경로를 적어도 됩니다. 그 파일에 다른 키가 있어도 읽지 않습니다. `selftest`에 토큰이 있는지 나옵니다.
5. `config.json`의 `bin`은 Homebrew로 설치한 macOS 기준 경로입니다(`/opt/homebrew/bin/claude`, `/opt/homebrew/bin/codex`). 자기 환경에 맞게 바꾸세요. ChatGPT 데스크톱 앱이 설치하는 `~/.local/bin/codex`가 PATH에서 먼저 잡힐 수 있는데, 앱과 함께만 업데이트되는 이전 버전(측정 시작 시점 0.148 알파)은 gpt-6 모델을 거부하므로 절대경로로 지정하는 편이 안전합니다.

## 쿼터

- quality 한 번 = 과제 3개 × 대상 2개. **평소 내가 쓰는 사용량 한도를 같이 깎습니다.** 같은 계정으로 다른 도구나 봇을 돌리고 있다면 그것들과도 한도를 나눠 씁니다.
- 실측(Codex Plus, Astra high): 과제 6개를 한 번 돌리니 5시간 한도의 약 25%, 주간 한도의 약 4%를 썼습니다. 어려운 3개만이면 그 3분의 2쯤(5시간 약 16%, 주간 약 2.5%)으로 추정되고, 6시간 간격(하루 4회)이면 주간 한도를 하루 약 10% 씁니다. Claude는 과제 6개에 5시간 약 3%, 주간 약 1%였습니다.
- 한도가 빠듯하면 `quality_every_hours`를 늘리세요. 단 측정 시각 구성이 바뀌므로 아래 "분석 기준"의 변경 기록에 남겨야 합니다.
- 한도에 걸린 실행은 점수 0이 아니라 `rate_limited` 상태로 따로 집계되고, 버거타임 판단(서버 오류율)에서도 빠집니다. 사용률 95% 이상에서 찍힌 기록도 분석에서 기본 제외됩니다.

## 분석

```bash
python3 analyze.py
python3 analyze.py --burger 0-5 --since 2026-10-20 --csv out.csv
```

- 대상별로 한국시간 0~23시 표가 나옵니다. `*`가 버거타임(기본 01~06시)입니다.
- "버거타임 vs 나머지"에서 서버 오류율 차이, 첫 응답 시간 비율, 점수 차이(과제 난이도 보정), thinking 토큰·도구 호출 수 비율을 비교합니다. 대괄호는 95% 신뢰구간이고 `<- 유의`가 붙으면 우연으로 보기 어려운 차이입니다.
- 신뢰구간은 **묶음 단위**로 계산합니다. 한 번의 과제 실행에서 나온 기록들, 같은 날의 ping들은 같이 움직이기 때문에 하나하나를 독립 표본으로 치면 하룻밤 사고 하나가 "유의"로 나옵니다. 그래서 quality는 실행 단위, ping은 날짜 단위로 묶고, 최소 표본(`--min-n`, 기본 10)도 묶음 수 기준입니다. ping은 10일, quality는 버거타임 실행 10회(03시 측정이 하루 1번이라 10일)가 쌓여야 판정이 나옵니다.
- **서버 오류율**은 overloaded·timeout·CLI 오류만 셉니다. 사용량 한도(`rate_limited`)는 내가 언제 많이 쓰느냐에 따라 생기므로 따로 개수만 보여 주고 판단에서는 뺍니다.
- "미국 평일만"도 따로 봅니다. 버거타임 가설이 맞다면 미국 주말보다 평일에서 차이가 더 커야 합니다.
- 기본으로 빼는 기록: 손으로 돌린 것·calibrate(한 시각에 몰려 있음, `--all-triggers`로 포함), 맥이 잠들었다 깬 직후(`--include-after-gap`), 과제 실행 중에 찍힌 ping(같은 계정에 요청이 몰린 상태, `--include-overlap`).
- Codex의 thinking 토큰(`reasoning_output_tokens`)은 실제 추론량보다 훨씬 작게 찍혀서(high effort 95초 과제에 146) 참고용입니다. Codex는 도구 호출 수·소요 시간·출력 토큰을 더 믿으세요.
- 최소 2~3주는 쌓으세요.
- `--verdict round1`: `--since`/`--until` 구간에 사전 등록 규칙 1~4를 적용한 판정표를 기존 출력 뒤에 붙입니다. 전반·후반은
  구간을 반으로 나눠 계산합니다. 미국 평일 효과 ÷ 주말 효과, 부트스트랩 p값, Holm 보정 p값도 참고값으로 나옵니다(등록 규칙 밖).
- `--score-timeouts`: 과제 제한시간에 걸린 실행도 그 시점 점수·소요 시간·thinking 추정치로 포함하고, 제한시간 도달 비율을
  따로 비교합니다(2차용). 이때 과제의 제한시간 도달은 서버 오류로 세지 않습니다.
- `--regrade results/regrade.jsonl`: `run_bench.py regrade`로 다시 채점한 점수의 중앙값을 씁니다.
- `--drop-active-pings`: 직전 기록보다 계정의 5시간 사용량이 `--active-delta`(기본 0.03 = 3%p) 이상 오른 ping을 뺍니다
  (2차 민감도 분석). 뺀 ping 수와 버거타임·나머지별 비율을 맨 위에 보여 줍니다.
- 2차 기록에는 핑의 단계별 시간(`t_model_sec` 모델 응답, `t_prep_sec` CLI 준비)과 통신 시간(`net_ttfb_ms`) 비교 줄이 더 나옵니다.

- **CLI 업데이트·모델 교체**는 시간대와 무관한 변화입니다. 분석 맨 위에 CLI 버전별 기간이 나오니, 바뀐 시점 이후만 보려면 `--since`를 쓰세요. `claude-opus-5-5`처럼 모델을 풀네임으로 고정해 둔 것도 그 때문입니다 (`opus` 같은 별칭은 새 모델이 나오면 가리키는 대상이 바뀝니다).
- **모델 바꿔치기 검출의 한계**: Codex는 클라이언트가 세션 로그에 적은 모델이라, 클라이언트 쪽에서 Sol로 돈 경우(openai/codex#42853 같은)는 잡지만 서버 내부에서 바꿔치기하는 건 못 잡습니다. Claude는 API 응답에 찍힌 model을 봅니다.
- **측정 환경 격리**: Claude는 `--safe-mode`(CLAUDE.md·MCP·훅·플러그인 끔)로, Codex는 `--ignore-user-config --ignore-rules`(config.toml과 실행 규칙 파일 무시)로 돌립니다. 내 설정을 바꿔도 결과에 섞이지 않게 하려는 것입니다. 다만 `~/.codex/AGENTS.md`는 여전히 읽힐 수 있으니 측정 기간엔 바꾸지 마세요.
  `--ignore-user-config`로도 OpenAI가 원격으로 내려주는 플러그인 목록과 `~/.codex/skills`의 스킬 목록은 지시문에 들어갑니다. 1차 Codex 핑은 이 때문에 요청이 두 종류로 섞였습니다(위 "사후 분석"). 2차부터는 `codex_config_overrides`로 원격 플러그인·apps·plugins를 끄고, 요청 구성의 해시(`prompt_hash`)를 기록합니다. 스킬을 설치하거나 지우면 해시가 바뀌니 측정 기간엔 건드리지 마세요.
  `--safe-mode`도 `~/.claude/settings.json`의 일반 설정(권한, 샌드박스, `advisorModel` 등)은 그대로 적용합니다. advisor를 켜면 측정 대상 모델이 과제 중에 다른 모델에게 조언을 받아 시간과 토큰이 섞이므로, 측정기는 `--settings '{"advisorModel":""}'`로 advisor를 끄고 돌립니다. 그 밖의 `settings.json` 설정도 측정 기간엔 바꾸지 마세요.
- **권한**: 과제는 매번 새 임시 폴더에서 돕니다. Claude는 그 폴더의 파일 편집과 `python3`/`python` 실행만 허용되고, Codex는 workspace-write 샌드박스 안에서 돕니다.
- 같은 프롬프트를 반복하므로 프롬프트 캐시가 적용됩니다(`cached_input_tokens`로 기록).

## 명령

| 명령 | 하는 일 |
|---|---|
| `python3 run_bench.py selftest` | 채점기·CLI 점검 (쿼터 0) |
| `python3 run_bench.py ping` | 지금 ping 한 번 |
| `python3 run_bench.py quality [--target NAME] [--task ID]` | 지금 과제 실행 |
| `python3 run_bench.py calibrate --repeat N` | 과제 N번 반복해 난이도 확인 |
| `python3 run_bench.py regrade [--repeat 3]` | 보관한 작업 폴더를 지금의 숨은 테스트로 다시 채점 (쿼터 0, `results/regrade.jsonl`) |
| `python3 run_bench.py status` | 최근 기록 보기 |
| `python3 analyze.py` | 시간대별 분석 |
| `python3 analyze.py --since ... --until ... --verdict round1` | 사전 등록 규칙으로 판정표까지 |
| `./install.sh` / `./uninstall.sh` | launchd 등록 / 해제 (기록은 남음) |

## 설정 (`config.json`)

- `targets`: 측정 대상. `claude-fable`은 기본으로 꺼져 있습니다(`"enabled": false`). 켜려면 `true`로 바꾸고, 가능하면 모델 풀네임으로 고정하세요. 대상마다 `"bin"`(실행 파일 절대경로), `"extra_args"`, `"ping": false`, `"quality": false`를 줄 수 있습니다.
- `effort`: 과제용 추론 강도, `ping_effort`: ping용 (동봉 config.json 값은 low, 빼면 CLI 기본값)
- 그 밖에 `tasks`(쓸 과제 목록), `quality_every_hours`, `ping_timeout_sec`(180), `task_timeout_sec`(900), `keep_raw`(원본 출력 보관), `codex_ignore_user_config`가 있습니다.
- `codex_config_overrides`: Codex는 측정 격리를 위해 `config.toml`을 무시하므로, 꼭 필요한 설정만 여기에 `"키=값"` 문자열로 넣습니다. 2차부터 기본값은 원격 플러그인 목록이 요청에 끼어들지 않게 하는 `["features.remote_plugin=false", "features.apps=false", "features.plugins=false"]`입니다(1차는 비어 있었음). Windows에서 돌린다면 `"windows.sandbox=\"elevated\""`도 넣어야 샌드박스가 명령을 막지 않습니다.
- `parallel_quality`: `false`면 과제를 두 CLI가 차례로 풉니다(2차 기본값). `true`면 1차처럼 동시에 풉니다.
- `net_probe`: 핑 직전에 API 호스트까지의 통신 시간을 잽니다(기본 켬). 대상마다 `"net_probe_host"`로 호스트를 바꿀 수 있습니다.
- `disable_cli_autoupdate`: 측정기가 띄운 claude에 `DISABLE_AUTOUPDATER=1`을 넘깁니다(기본 켬).
- `expected_cli_versions`: `{"claude": "2.1.327", "codex": "0.170.0"}`처럼 적으면 다른 버전으로 돈 기록에 `version_drift`가 붙습니다. 비워 두면 표시하지 않습니다.
- `ping_interval_min`을 바꿨으면 `./install.sh`를 다시 실행하세요. 나머지는 다음 실행부터 바로 반영됩니다.
- 과제 파일을 고치면 `task_version`이 바뀌어 기록에 남습니다.
